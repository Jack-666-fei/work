## 1. 做了什么

补上了此前缺失的那一环——**把「检索」和「生成」连起来**,并给模型定角色。

| # | 内容 | 文件 |
|---|---|---|
| 1 | **RAG 检索增强 advisor**(新增) | `advisor/KnowledgeBaseAdvisor.java` |
| 2 | **system prompt 角色设定**(新增) | `resources/prompts/system-prompt.txt` |
| 3 | 把 advisor 挂进 ChatClient,并理清与记忆 advisor 的顺序 | `config/ChatConfig.java` |
| 4 | 知识库清空接口(为去重/重导提供手段) | `KnowledgeBaseService.clear()`、`POST /api/kb/clear` |
| 5 | **分块修复:标题并入正文再向量化** | `KnowledgeBaseService.buildChunks()` |
| 6 | RAG 相关配置项 | `application.properties` |

改造后的链路:

```
用户提问
  ↓
KnowledgeBaseAdvisor   ← 查 Milvus,把资料拼进 system 消息   ★本次新增
  ↓
MessageChatMemoryAdvisor ← 带上历史对话
  ↓
模型 → 回答
```

## 2. 为什么没用 QuestionAnswerAdvisor

Spring AI 官方的 `QuestionAnswerAdvisor` 在 `spring-ai-advisors-vector-store` 模块里,而该 jar
**既不在本地 `.m2` 仓库、也不在项目 classpath 上**。这台机器**没有安装 Maven**,新增依赖需要联网拉取并手工铺进仓库,风险高、代价大。

因此改为**自己实现一个等价的 advisor**,只使用现有 classpath 上的类,不引入任何新依赖。功能上与官方实现一致:检索 → 拼装 system → 调用模型。

---

## 3. advisor 的顺序(关键设计点)

反编译 `MessageChatMemoryAdvisor` 后确认,它的 `before()` 末尾是:

```java
Message lastUserMessage = processedRequest.prompt().getLastUserOrToolResponseMessage();
this.chatMemory.add(conversationId, lastUserMessage);   // 存"最后一条用户消息"
```

而各 advisor 的 order 是:

| advisor | order |
|---|---|
| `MessageChatMemoryAdvisor` | `DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER` = **-2147483448**(几乎最外) |
| **`KnowledgeBaseAdvisor`(本实现)** | `DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER + 100` |
| `ChatModelCallAdvisor` | `Integer.MAX_VALUE` = 2147483647(最内) |

**本 advisor 必须排在记忆 advisor 的内层**。否则记忆 advisor 写进会话记忆的会是"用户原话 + 检索到的资料",导致记忆被资料撑爆、并污染后续所有轮次。放在内层后,记忆里存的始终是用户原话,只有发给模型的那一份被增强。

这个顺序不是可选的优化,放反了会直接损坏会话记忆。

## 4. 实测结果

### 4.1 生效的部分 ✅

| 场景 | 表现 |
|---|---|
| **手册内 + 检索命中** | 问"新生要把户口迁到学校吗?" → 回答引用了手册内容:"根据【参考资料】中的'户口迁移相关规定':新生入学后,学校统一办理新生落户。提交落户材料包括:录取通知书(第二联)、户口迁移证(福建省外户籍新生提交)…" |
| **无关问题** | 问"用 Java 写个快速排序" → "我只负责回答「集美大学 2025 级新生入学手册」中的问题。"(system prompt 第 3 条生效) |
| **资料中没有的内容** | 问"那档案呢?" → "手册中未提及…建议您咨询学校相关部门"(第 2 条生效,不再编造) |
| **多轮记忆** | 仍然正常,与 RAG 共存 |
| **过程可观测** | 每轮日志输出:`RAG 检索: query="…" 命中=5 条, 拼入参考资料 1429 字` |
| **数据干净** | 清空重复后重导,**89 条,无重复**(原为 178 = 89×2) |

### 4.2 没解决的部分 ⚠️ 检索召回率低

即使手册里明确有内容,检索也经常召不回:

| 查询 | 期望章节 | 结果 |
|---|---|---|
| `接站` | 接站程序 | ❌ 未命中(topK 提到 30 仍不命中) |
| `报到时间` | 报到时间 | ❌ 未命中 |
| `新生什么时候报到？` | 报到时间 | ❌ 未命中 |
| `学费` | 收费标准 | ❌ 未命中 |
| `2、接站程序` | 接站程序 | ✅ #2 |
| `本科学费一年多少钱？` | 收费标准 | ✅ #1 |
| `户口迁移` | 户口迁移 | ✅ #1 |
| `新生要把户口迁到学校吗？` | 户口迁移 | ✅ #4 |
| `航海学院报到点在哪` | 航海学院 | ✅ #2 |
| `那档案呢？`(多轮追问) | 档案转移 | ❌ 未命中 |

约 **6/10 命中**,且规律不可靠(同为短词,"户口迁移"能中而"报到时间"不能)。

### 4.3 根因:嵌入模型对中文几乎没有区分能力

直接调 LM Studio 的 embedding 接口做余弦相似度测量:

```
中文:
  「接站」 vs 接站程序片段(相关)   cosine = 0.6131
  「接站」 vs 档案转移片段(无关)   cosine = 0.6857   ← 无关的反而更高!

英文对照:
  相关句对  0.7424
  无关句对  0.4092                     ← 分离度 0.33,非常清晰
```

**所有中文都挤在 0.6~0.69 的窄带内,排序基本随机;英文则能干净分离。**
当前嵌入模型 `text-embedding-nomic-embed-text-v1.5` 是**以英文为主**训练的,没有可用的中文语义能力。

**这是当前 RAG 效果的最大瓶颈,而不是代码问题。**

## 5. 顺带修复:分块时标题被丢弃

`buildChunks()` 原本把 Markdown 标题**从正文中剥离,只存进 metadata**,于是向量化的是不含标题的正文。

后果非常直接:

- 章节「1、报到时间」的正文只有 `2025年9月10日7:30-17:30` —— **里面根本没有"报到""时间"两个字**,查"报到时间"自然召不回
- 章节「收费标准」的正文是一串金额数字,查"学费"同理召不回

已修复为**把标题并入正文一起向量化**:

```java
String text = heading.isEmpty() ? body : heading + "\n" + body;
```

这是 RAG 分块的通行做法(让每个片段自带章节语义)。修复已生效(可在检索结果中看到片段以标题开头),但由于嵌入模型对中文本身无区分能力,单靠这个修复不足以扭转召回率。

## 6. 下一步建议(按性价比排序)

| # | 措施 | 说明 |
|---|---|---|
| **1** | **换一个支持中文的嵌入模型** ← 收益最大 | 例如 `bge-m3`、`Qwen3-Embedding-0.6B`、`text-embedding-bge-large-zh-v1.5`、`multilingual-e5-large`。需在 LM Studio 里下载,**随后要同步改 `embedding-dimension` 并重建集合、重新导入**(向量维度在建集合时固定,不能原地改) |
| 2 | 追问重写 | "那档案呢?" 这类依赖上下文的短追问召不回。可在检索前用对话模型把追问改写成独立问句再检索(多一次模型调用,4GB 显存下会增加延迟) |
| 3 | 提高 topK / 调相似度阈值 | 当前 `top-k=5`、阈值 `0.0`。但实测把 topK 提到 30 仍召不回"接站",说明单靠这个解决不了 |
| 4 | 混合检索(向量 + 关键词) | Milvus 支持稀疏向量/全文检索,可作为向量召回的兜底。实现成本较高 |

换嵌入模型后的操作步骤(留待执行):

```powershell
# 1) 在 LM Studio 下载并加载中文嵌入模型
# 2) 改 application.properties:
#    spring.ai.openai.embedding.options.model=<新模型>
#    spring.ai.vectorstore.milvus.embedding-dimension=<新维度>
# 3) 重建集合(维度变了,不能原地改):
#    Milvus REST: POST /v2/vectordb/collections/drop  {"collectionName":"jmu_handbook"}
# 4) 重启应用(initialize-schema=true 会按新维度重建)
# 5) 重新导入:/api/kb/import
```

## 7. 本轮踩到的环境坑

### 7.1 手动 javac 不会拷贝资源(已导致配置静默失效)

`target/classes/application.properties` 曾长期是旧版本 —— 因为手动 `javac` 只编译 `.java`,**不会把 `src/main/resources` 拷到 `target/classes`**。IDEA 构建会自动做这一步,所以只在手工构建时表现为"改了配置没生效"。

本次已修正:每次编译后追加

```powershell
Copy-Item "$rag\src\main\resources\*" "$rag\target\classes\" -Recurse -Force
```

### 7.2 控制台日志中文乱码

日志里 `query="����Ҫ�ѻ���Ǩ��ѧУ��"` 是控制台代码页(GBK)与 UTF-8 输出不一致导致的**显示问题**,数据本身正确。若要让日志文件可读,可显式指定 logback 编码。

### 7.3 `/api/kb/clear` 的实现依据

Milvus 上按 metadata 过滤删除确实可行:`vectorStore.delete(eq("collection", "jmu_handbook"))` 实测把 178 条清到 **0 条**。
