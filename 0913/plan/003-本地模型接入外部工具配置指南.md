# 003 · 把本地 LM Studio 模型接入外部工具(Codex / Claude Code 等)

> 目标机器(服务端):当前这台 Windows,LM Studio **0.4.23**,监听 1234
> 场景:另一台机器上的 Codex CLI / Claude Code / Cline 等,调用本机的本地模型
> 编写日期:2026-09-10

## 0. 先看这个:核心参数速查表

你说缺的就是这几个。**本机**用第一列,**另一台机器**用第二列。

| 参数 | 本机访问 | 另一台机器访问 |
|---|---|---|
| **接入地址(OpenAI 兼容)** | `http://127.0.0.1:1234/v1` | `http://10.22.32.85:1234/v1` |
| **接入地址(Anthropic 兼容)** | `http://127.0.0.1:1234` | `http://10.22.32.85:1234` |
| **接入地址(原生 REST)** | `http://127.0.0.1:1234/api/v0` | `http://10.22.32.85:1234/api/v0` |
| **API 密钥** | `lm-studio` | `lm-studio` |
| **对话模型名** | `google/gemma-4-e2b` | 同 |
| **嵌入模型名** | `text-embedding-nomic-embed-text-v1.5` | 同 |

### 关于密钥 —— 这是最容易困惑的一点

**LM Studio 默认不校验密钥,但绝大多数客户端强制要求填。**

所以规则是:**填任意非空字符串都可以**,惯用 `lm-studio` / `sk-lm-studio` / `sk-no-key-required`。

之所以不能留空:Codex、Claude Code、Continue 这类工具如果拿不到 key 会直接拒绝启动,blank 会被当成配置错误。填个占位符就行。

> 如果确实想要真校验:LM Studio 里打开 **Require Authentication**,它会生成一个真 token(存在 `~/.lmstudio/.internal/lms-key-2`)。校园网环境下**建议开启**,见 §6。

## 1. 为什么现在跨机器连不上

当前绑定状态(已实测):

```
Get-NetTCPConnection -LocalPort 1234 -State Listen
  LocalAddress  LocalPort
  127.0.0.1     1234          ← 只监听回环地址
```

对应的配置文件 `~/.lmstudio/.internal/http-server-config.json`:

```json
{
  "autoStartOnLaunch": true,
  "port": 1234,
  "cors": false,
  "networkInterface": "127.0.0.1",     ← 元凶
  "justInTimeModelLoading": true
}
```

`networkInterface` 为 `127.0.0.1` 时,只有本机能连。这就是"另一台机器连不上"的原因。

## 2. 第一步:让 LM Studio 监听局域网

### 方式 A(推荐,图形界面)

LM Studio 左侧栏点 **Developer**(`</>` 图标)→ 顶部找到 **Server Settings**,打开:

- ✅ **Serve on Local Network**(允许局域网访问)← 必须开
- ⬜ **Require Authentication**(要求密钥)← 校园网建议开
- ⬜ **Enable CORS**(跨域)← 只有浏览器型客户端才需要,见 §6
- **Server Port** 保持 `1234`

### 方式 B(改配置文件)

关闭 LM Studio,编辑 `<用户目录>\.lmstudio\.internal\http-server-config.json`:

```json
"networkInterface": "0.0.0.0"
```

保存后重新打开 LM Studio。`0.0.0.0` 表示监听所有网卡。

> ⚠️ 注意:`http-server.json`(另一个文件)里的 `host`/`pid`/`port` 是运行时状态,**不要去改它**,改 `http-server-config.json`。

### 验证

改完后再查一次,`LocalAddress` 应变成 `0.0.0.0`:

```powershell
Get-NetTCPConnection -LocalPort 1234 -State Listen | Select-Object LocalAddress, LocalPort
```

## 3. 第二步:放行 Windows 防火墙

本机当前状态(已实测):

```
防火墙配置:   Public = Enabled (开启)
网络类型:     WLAN → NetworkCategory = Public     ← 关键
现有规则:     无 1234 相关规则
```

WLAN 被归类为 **Public**,而 Public 配置文件是开启的、入站默认拦截。所以即使 LM Studio 监听 `0.0.0.0`,外部请求也会被防火墙丢掉。

在**服务端(这台机器)**的**管理员** PowerShell 里执行:

```powershell
New-NetFirewallRule -DisplayName "LM Studio API Server (1234)" `
  -Direction Inbound -Protocol TCP -LocalPort 1234 `
  -Action Allow -Profile Any
```

`-Profile Any` 是必须的 —— 因为 WLAN 是 Public,只写 `Private` 会不生效。

要撤销:

```powershell
Remove-NetFirewallRule -DisplayName "LM Studio API Server (1234)"
```

> 更严格的做法:把入站限制到特定来源 IP,而不是对全网段开放:
> ```powershell
> New-NetFirewallRule -DisplayName "LM Studio API Server (1234)" `
>   -Direction Inbound -Protocol TCP -LocalPort 1234 -Action Allow `
>   -Profile Any -RemoteAddress 10.22.32.0/24
> ```

## 4. 第三步:在另一台机器上验证连通

先做最基本的连通性测试,再去配工具。**这一步能省掉后面大量瞎折腾。**

```powershell
# 1) 端口通不通
Test-NetConnection 10.22.32.85 -Port 1234

# 2) 列出模型(最关键的验证)
curl.exe -s http://10.22.32.85:1234/v1/models

# 3) 实际发一句话
curl.exe -s -X POST http://10.22.32.85:1234/v1/chat/completions `
  -H "Content-Type: application/json" `
  -H "Authorization: Bearer lm-studio" `
  --data-binary '{\"model\":\"google/gemma-4-e2b\",\"messages\":[{\"role\":\"user\",\"content\":\"say OK\"}],\"max_tokens\":20}'
```

第 2 步能返回模型列表,才说明网络链路通了。

## 5. 各工具的配置

### 5.0 WorkBuddy(腾讯 CodeBuddy 系桌面工作台)

**配置路径:Settings → Models → Custom Models → Add Model**

| WorkBuddy 字段 | 填入值 |
|---|---|
| Provider | `Custom` |
| **Interface Address** | `http://127.0.0.1:1234/v1/chat/completions`(本机)<br>`http://10.22.32.85:1234/v1/chat/completions`(另一台机器) |
| **API KEY** | `lm-studio` |
| **Model Name** | `google/gemma-4-e2b` |
| Tool Calling | ✅ **开启** —— 已实测该模型经 LM Studio 支持 function calling |
| Inferior Mode(推理模式) | ✅ 可以开 —— 响应中带 `reasoning_content`(有可见思考过程) |
| Image Input | ⬜ 可选。模型本身是 VLM(`type=vlm`),但非必需 |
| **Custom Protocol** | ⬜ **保持关闭** —— 关闭时 WorkBuddy 才按 OpenAI 标准校验路径 |
| 上下文窗口 Input / Output | 留 **Use Provider Default** |

#### ⚠️ 这个工具最容易填错的地方

**Interface Address 必须包含完整的 `/chat/completions` 路径**,不能只填到 `/v1`。

这是 WorkBuddy 特有的要求 —— 大多数工具(Codex、Cline、SDK)要的是**不带路径**的 base URL,而 WorkBuddy 要**带完整路径**。填错会直接 4xx。

```
✅ http://10.22.32.85:1234/v1/chat/completions
❌ http://10.22.32.85:1234/v1
❌ http://10.22.32.85:1234
```

#### 实测结论

| 能力 | 结果 |
|---|---|
| `/v1/chat/completions` | ✅ HTTP 200 |
| **Tool Calling** | ✅ **支持**,返回规范的 `tool_calls` + `finish_reason: "tool_calls"` |
| 推理过程 | ✅ 响应含 `reasoning_content` 字段 |

WorkBuddy 的配置(含 API Key)保存在本地 `workbuddy/models.json`,不上传云端。

> 如果 WorkBuddy 报跨域错误:LM Studio 配置里 `cors: false`,可在 Server Settings 里打开 **Enable CORS** 再试。

### 5.1 Codex CLI

配置文件 `~/.codex/config.toml`(Windows 是 `C:\Users\<你>\.codex\config.toml`):

```toml
model = "google/gemma-4-e2b"
model_provider = "local"

[model_providers.local]
name = "LM Studio (Local)"
base_url = "http://10.22.32.85:1234/v1"
wire_api = "responses"
env_key = "LMSTUDIO_API_KEY"
```

然后设置环境变量:

```powershell
$env:LMSTUDIO_API_KEY = "lm-studio"      # 当前会话
[Environment]::SetEnvironmentVariable("LMSTUDIO_API_KEY","lm-studio","User")   # 永久
```

**三个必踩的坑**(已核实):

1. **`wire_api` 必须是 `"responses"`。** Codex 在 2026 年 2 月移除了 `"chat"` 协议,写 `wire_api = "chat"` 会**直接启动失败**。
   已实测本机 LM Studio **支持 `/v1/responses`**(HTTP 200),所以这条路走得通。

2. **provider id 不能用 `openai` / `ollama` / `lmstudio`** —— 这三个是保留名,会冲突。上面用 `local` 就是为了避开。

3. **`model_provider` 和 `model_providers` 只在用户级 `~/.codex/config.toml` 生效**;写在项目里的 `.codex/config.toml` 会被忽略并告警。

参考:[Codex CLI with OpenRouter](https://openrouter.ai/blog/tutorials/codex-cli-openrouter/)、[Codex config.toml 详解](https://ofox.ai/blog/codex-cli-config-toml-deep-dive)

## 6. 三个必须知道的警告

### 6.0 【已解决】WorkBuddy 报 `exceed_context_size_error`

**现象**(2026-09-10 实测):

```
Engine protocol predict request returned 400:
request (32620 tokens) exceeds the available context size (8192 tokens),
try increasing it
n_prompt_tokens: 32620, n_ctx: 8192
Error Code: 10000
```

连接测试成功、但一对话就报错。**原因不是配置错,是上下文不够。**

WorkBuddy 是 agent 型工具,一次请求就把系统提示 + 工具定义 + 项目上下文全带上,
实测单次 **32620 token**;而模型当时只加载了 **8192**。

**修复:以更大的上下文重新加载模型。**

LM Studio 的加载 API(不是 OpenAI 兼容接口):

```powershell
# POST /api/v1/models/load —— body 要用文件传,直接内联会被 PowerShell 的引号处理弄坏
$body = '{"model":"google/gemma-4-e2b","context_length":65536,"flash_attention":true}'
[System.IO.File]::WriteAllText("$env:TEMP\load.json", $body, (New-Object System.Text.UTF8Encoding($false)))
curl.exe -s -X POST http://127.0.0.1:1234/api/v1/models/load `
  -H "Content-Type: application/json" --data-binary "@$env:TEMP\load.json"
```

**实测结果:**

| 项 | 值 |
|---|---|
| 上下文 8192 → **65536** | 加载耗时 16.9s |
| 显存占用 | **2010 / 4096 MiB**(余量充足) |
| **34024 token 的请求** | ✅ **HTTP 200,44.2s**(已超过 WorkBuddy 所需的 32620) |
| 中文 token 换算 | 约 **0.57 token/字**(6 万汉字 ≈ 3.4 万 token) |
| `parallel: 4` 是否平分上下文 | **不会**,单请求仍可用满 65536 |

**两个必须注意的点:**

1. **`load` 不会替换旧实例,而是新建一个。** 反复 load 会堆积多个实例把显存吃满
   (实测出现过 8192 + 32768 两个实例并存,显存 3937/4096)。
   加载后要显式卸掉旧的:

   ```powershell
   $body = '{"instance_id":"google/gemma-4-e2b:2"}'
   [System.IO.File]::WriteAllText("$env:TEMP\unload.json", $body, (New-Object System.Text.UTF8Encoding($false)))
   curl.exe -s -X POST http://127.0.0.1:1234/api/v1/models/unload `
     -H "Content-Type: application/json" --data-binary "@$env:TEMP\unload.json"
   ```

   查看所有实例:`curl.exe -s http://127.0.0.1:1234/api/v0/models`

2. **这个设置不持久。** 模型一旦被卸载/驱逐或 LM Studio 重启,会按全局默认 JIT 加载回 8192
   (`~/.lmstudio/settings.json` 里的 `defaultContextLength.value = 8192`)。
   要让 64K 长期生效,需在 **LM Studio 图形界面里改默认上下文长度**。

**性能代价:** 处理 3.4 万 token 的 prompt 要 **44 秒**。这是 4GB 显卡的固有成本 ——
WorkBuddy 每轮都要重新灌一次完整上下文,所以每次响应都会明显偏慢。

### ⚠️ 6.1 模型能力:它当不了编码助手

`google/gemma-4-e2b` 的真实参数(已实测):

| 属性 | 值 | 问题 |
|---|---|---|
| 参数量 | 约 2B(e2b),Q4_K_M 量化 | **太小** |
| **已加载上下文** | **8192** | **这是致命项** |
| 模型上限 | 131072 | 但实际只加载了 8192 |
| 显存 | RTX 3050 **4GB** | 正是它把上下文压到 8K |

**Codex / Claude Code 是"agentic"工具**:它们会反复读仓库文件、执行命令、把工具输出塞回上下文。**实际消耗动辄 5 万~20 万 token。**

8192 的上下文意味着:稍微大一点的文件都读不进来,编码任务基本跑不动。

另外 8192 是 LM Studio 的全局默认值,来自 `~/.lmstudio/settings.json`:

```json
"defaultContextLength": { "type": "custom", "value": 8192 }
```

**建议:**
- 想真正拿它写代码 → 换一个代码模型(如 Qwen2.5-Coder 系列),并尽量调大上下文
- 4GB 显存是硬约束。7B 模型装得下但上下文开不大;想吃长上下文需要更强的显卡或更小的量化
- **把它用在纯对话 / 问答场景**(比如前面的 RAG 项目)是合适的;当 agent 编码后端不合适

### ⚠️ 6.2 你现在在校园网上(`XMUT`)

WLAN 的 SSID 是 **`XMUT`**(集美大学校园网),IP `10.22.32.85`。

两个后果:

1. **可能根本连不通。** 校园网 AP 普遍开启**客户端隔离(AP isolation)**,同一 WiFi 下的设备之间也互相不可见。这种情况下无论防火墙怎么配都没用。
   - 先用 §4 的 `Test-NetConnection` 试一下,不通且 `ping` 也不通,基本就是这个原因
   - 绕法:两台机器接同一个路由器/手机热点,或走 VPN/Tailscale 之类的组网

2. **安全风险。** 打开 `Serve on Local Network` 后,同一网段内的**其他同学可能访问到你的模型服务**。校园网尤其不建议裸奔。
   **务必同时打开 `Require Authentication`**,并把防火墙规则的 `-RemoteAddress` 限制到你自己设备的 IP。

### ⚠️ 6.3 CORS 默认关闭

配置里 `"cors": false`。

- CLI 工具(Codex / aider / 脚本)**不受影响**
- **浏览器里跑的网页版客户端会失败**(跨域被拦)

如果要用浏览器型客户端:LM Studio 里打开 **Enable CORS**。

## 7. 排错对照表

| 现象 | 原因 | 解决 |
|---|---|---|
| `Test-NetConnection` 失败 | LM Studio 仍监听 127.0.0.1 | §2 打开 Serve on Local Network |
| 端口通但请求超时/被拒 | 防火墙拦了(Public profile) | §3 加规则,注意 `-Profile Any` |
| 一切都配了还是不通 | 校园网 AP 隔离 | 换网络 / 热点 / 组网 |
| `401 / Unauthorized` | 开了 Require Authentication 但 key 不对 | 用 `lms-key-2` 里的真 token,而不是 `lm-studio` |
| Codex 启动即失败 | `wire_api = "chat"` | 改成 `"responses"` |
| Codex 报 provider 冲突 | 用了保留名 | 换 `local`、`myserver` 等 |
| 项目级 config.toml 不生效 | 位置不对 | 挪到用户级 `~/.codex/config.toml` |
| `model_not_found` | 模型名不精确 | 必须完整写 `google/gemma-4-e2b`,不能只写 `gemma` |
| 回答被截断 / 报上下文超限 | 8192 上下文 | §6.1 |
| 浏览器客户端跨域报错 | `cors: false` | 打开 Enable CORS |

## 9. 一句话总结

**参数本身很简单**:地址 `http://<本机IP>:1234/v1`、密钥填 `lm-studio`、模型名 `google/gemma-4-e2b`。

真正要做的其实是三件事:打开 LM Studio 的局域网开关、放行防火墙、确认校园网没做设备隔离。

但最需要提前知道的:**8192 上下文 + 2B 参数的模型当 Codex / Claude Code 的后端基本不可用**,协议能通、任务跑不动。它更适合做纯对话和 RAG 问答。
