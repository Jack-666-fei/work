### 1.2 最要命的一点:召回内容完全不可见

`KnowledgeBaseAdvisor.buildContext()` 拿到 `List<Document>` 后,只打了一行:

```java
log.info("RAG 检索: query=\"{}\" 命中={} 条, 拼入参考资料 {} 字", ...);
```

**召回的具体内容、相似度分数、章节名、排名 —— 全部丢弃,一个字都没打。**

回忆一下代价:`002` 里排查"为什么问接站答不出来"时,我们不得不
另外写脚本、直接调 `/api/kb/search`、再手工比对 embedding 余弦相似度,才最终定位到

**如果当时日志里就打着每条召回的分数和内容,这个问题几分钟就能看出来。**
这正是本次需求的直接价值。

## 2. 核心需求:详细召回日志

### 2.1 要打印什么(尽可能详细)

一次检索涉及的**全部信息**:

| # | 字段 | 为什么重要 |
|---|---|---|
| 1 | 检索 query(原文) | 确认拿去检索的到底是哪句话 |
| 2 | topK、相似度阈值、集合名 | 复现当时参数 |
| 3 | 命中条数 / 去重后条数 | 判断有没有召回 |
| 4 | **每条命中的相似度分数** | ★ **最关键**。分数低=没召回对,一眼看出 |
| 5 | **每条命中的排名** | 看正确内容排第几 |
| 6 | **每条命中的章节名(heading)** | 一眼判断"检索对了没有" |
| 7 | **每条命中的完整正文** | ← 本次需求主体 |
| 8 | 每条正文长度 | 判断是否被截断 |
| 9 | 检索耗时 | 性能 |
| 10 | 是否因去重被丢弃 | 解释"命中5条却只用4条" |
| 11 | 最终拼入参考资料的总字数 | 上下文占用 |
| 12 | **⚠ 低分告警** | 最高分低于阈值时主动告警 |
| 13 | (最高级别)最终发给模型的完整 prompt | 判断是"检索没找到"还是"模型没用上" |

### 2.2 日志格式设计

```
2026-09-10 11:02:33.123 INFO [req=a1b2c3d4] [RAG] ===== 检索开始 =====
2026-09-10 11:02:33.124 INFO [req=a1b2c3d4] [RAG] cid=932214c3 query="新生报到流程和接站安排是怎样的？"
2026-09-10 11:02:33.124 INFO [req=a1b2c3d4] [RAG] 参数: topK=5 阈值=0.00 集合=jmu_handbook
2026-09-10 11:02:33.880 INFO [req=a1b2c3d4] [RAG] 检索完成: 命中 5 条, 耗时 756ms
2026-09-10 11:02:33.881 INFO [req=a1b2c3d4] [RAG] --- #1 排名=1 分数=0.6812 章节="接站程序" 长度=142 ---
2026-09-10 11:02:33.881 INFO [req=a1b2c3d4] [RAG] > 2、接站程序
2026-09-10 11:02:33.881 INFO [req=a1b2c3d4] [RAG] > 学校于2025年9月10日7:00-18:00在高崎机场、厦门北站安排接站，
2026-09-10 11:02:33.881 INFO [req=a1b2c3d4] [RAG] > 按学校片区分流新生，分别送至主校区光前体育馆南门……
2026-09-10 11:02:33.882 INFO [req=a1b2c3d4] [RAG] --- #2 排名=2 分数=0.6731 章节="档案转移" 长度=98 ---
2026-09-10 11:02:33.882 INFO [req=a1b2c3d4] [RAG] > 四、档案转移
2026-09-10 11:02:33.882 INFO [req=a1b2c3d4] [RAG] > 1. 全日制非定向研究生：必须转档案；……
2026-09-10 11:02:33.890 INFO [req=a1b2c3d4] [RAG] 去重: 命中 5 条 → 有效 4 条(丢弃 1 条重复正文)
2026-09-10 11:02:33.890 WARN [req=a1b2c3d4] [RAG] ⚠ 最高相似度仅 0.6812 < 建议阈值 0.75,本次检索可能未命中
2026-09-10 11:02:33.891 INFO [req=a1b2c3d4] [RAG] ===== 检索结束: 拼入参考资料 1429 字 =====
```

设计要点:

- 统一前缀 `[RAG]`,便于 `grep` 和过滤
- 正文每行加 `> ` 前缀,**多行内容仍可逐行 grep,不会把日志结构搞乱**
- 分数保留 4 位小数
- 低分告警用 **WARN 级别**,便于按级别过滤

### 2.3 详细程度分级(可配置)

内容全打会很占地方,所以做成**分档可调**:

```properties
# 召回日志详细程度: off | brief | full | prompt
#   off    = 不打召回内容(只留现有那行汇总)
#   brief  = query + 命中数 + 章节名 + 分数(不打正文)
#   full   = brief + 每条完整正文        ← 默认
#   prompt = full + 最终发给模型的完整 prompt(最详细,最占空间)
rag.logs.retrieval-level=full
# 单条正文打印上限(字符),防止超长片段刷屏;0 表示不截断
rag.logs.retrieval-max-chars=0
```

**默认给 `full`**(因为你的诉求是"尽可能详细")。

### 2.4 【我的建议】详细内容写入独立日志文件

这是我比较坚持的一个设计意见:

**不要把召回正文混进主日志。** 理由:

- 每次请求 1~5 条正文,动辄几千字,主日志会被瞬间淹没
- 排查别的问题(连接失败、启动异常)时,主日志会变得没法看
- 但召回内容又是排查 RAG 时最需要的

**方案:用独立 logger 名写独立文件。**

| 日志文件 | 内容 | 保留 |
|---|---|---|
| `logs/rag.log` | 主日志:请求、耗时、错误、**一行式检索汇总** | 7 天 |
| `logs/rag-retrieval.log` | **召回详情**:每条正文全文 | 3 天(更短) |
| `logs/rag-error.log` | 只收 ERROR | 7 天 |

两全其美:主日志保持清爽,详情完整保留,导出时两个都给。

> 如果你觉得分文件麻烦,也可以合并成一个文件 —— 说一声就行,这只是 `logback-spring.xml` 里加/减一个 appender 的事。

## 3. 其余日志补全

### 3.1 逐类清单

| 类 | 补什么 | 级别 |
|---|---|---|
| `ChatService` | 收到请求(会话ID、问题摘要、是否新会话) | INFO |
| | 完成(会话ID、耗时、回复字数) | INFO |
| | 异常(会话ID + 堆栈) | ERROR |
| `KnowledgeBaseAdvisor` | §2 的全部召回详情 | INFO/WARN |
| `ConversationService` | 清空会话 / 查看记忆 | INFO/DEBUG |
| `KnowledgeBaseController` | 导入、清空、检索的入参 | INFO/DEBUG |
| `KnowledgeBaseService` | 导入耗时、分块数量、清空条数 | INFO |

### 3.2 新增全局异常处理 `GlobalExceptionHandler`

`@RestControllerAdvice`:

- ERROR 级别记录**完整堆栈**(带 requestId)
- 返回**结构化错误响应**,而不是 Tomcat 默认的 500 页面

现在任何未捕获异常都只有容器记一条,响应体对调用方不友好。

### 3.3 新增请求追踪 ID(MDC)

轻量 `Filter`,为每个 HTTP 请求生成 8 位 `requestId` 放入 MDC:

- 日志格式带 `[req=a1b2c3d4]`
- 一次对话会跨 **Controller → Advisor → Service** 三个类,
  没有这个 ID,并发时日志交错在一起,根本分不清哪几行属于同一次请求
- 请求结束清理 MDC(避免线程池复用污染)

### 3.4 启动打印生效配置

`ApplicationRunner`,启动后打一行:

```
RAG 配置生效: enabled=true topK=5 阈值=0.00 记忆窗口=20 集合=jmu_handbook 模型=google/gemma-4-e2b 召回日志=full
```

避免"改了配置没生效"的困惑(这个坑我们踩过 —— `target/classes` 里的配置曾是旧版本)。

## 4. 日志落盘与轮转(`logback-spring.xml`)

| Appender | 文件 | 编码 | 轮转 |
|---|---|---|---|
| `CONSOLE` | 控制台 | **UTF-8** | — |
| `FILE` | `logs/rag.log` | **UTF-8** | 10MB / 天,保留 7 天 |
| `RETRIEVAL_FILE` | `logs/rag-retrieval.log` | **UTF-8** | 10MB / 天,保留 3 天 |
| `ERROR_FILE` | `logs/rag-error.log` | **UTF-8** | 10MB / 天,保留 7 天 |

格式:

```
%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%X{requestId}] [%thread] %logger{36} - %msg%n
```

包级别降噪:

```xml
<logger name="com.wuyunbin.rag" level="DEBUG"/>
<logger name="org.springframework.ai" level="WARN"/>
<logger name="io.milvus" level="WARN"/>
```

> **必须显式写 `<charset>UTF-8</charset>`**:Logback 的 FileAppender 默认跟随 `file.encoding`,
> 当前环境控制台是 GBK 而 Java 是 UTF-8,不指定就会写出乱码文件。

## 5. 导出日志接口(`/api/logs`)

```
GET /api/logs/files                        列出日志文件(名称/大小/时间)
GET /api/logs/tail?lines=200&level=ERROR   查看最近日志(最快,不用下载)
GET /api/logs/download?file=rag.log        下载单个文件
GET /api/logs/export                       打包全部日志为 zip 下载
```

- `tail` 支持 `level` 过滤、`lines` 上限 5000(**环形缓冲逐行读,不整file加载内存**)
- `export` 用 `java.util.zip.ZipOutputStream`(**零新依赖**),文件名自动带时间戳
- 大文件走流式输出

## 6. 安全设计(必须做)

导出接口是**文件读取**接口:

| 风险 | 对策 |
|---|---|
| **路径穿越** `?file=../../application.properties` | **文件名正则白名单** `^[A-Za-z0-9._-]+\.log(\.\d+)?$` + 解析后校验**规范路径确实位于日志目录内** |
| 日志含敏感信息(提问内容、文件路径、手册正文) | 默认**只允许本机访问**;可配置开关 |
| 内存爆掉 | `tail` 环形缓冲 + 上限;`download` 流式 |
| 磁盘涨爆 | Logback 轮转 + 保留天数 + 总量上限 |

```properties
rag.logs.export.enabled=true
rag.logs.export.localhost-only=true      # 建议保持 true（你在校园网环境）
rag.logs.tail.max-lines=5000
```

## 7. 我的意见与讨论点(重点)

以下是我作为实施方想提出的看法,请你判断:

### 💡 意见 1:召回日志里,**分数比正文更重要**

正文能告诉你"召回了什么",但**分数能告诉你"为什么是这些"**。

我们在 `002` 里发现嵌入模型对中文几乎无区分能力(相关 0.61 / 无关 0.69,**无关的反而更高**),
如果当时日志里就有分数,这个结论**几分钟就能得出**,而不是靠另外写脚本测余弦相似度。

所以我把「分数」列在需求表第 4 位,并且建议**默认就打印**。

### 💡 意见 2:建议加「低分告警」

```
⚠ 最高相似度仅 0.6812 < 建议阈值 0.75,本次检索可能未命中
```

**理由**:大多数人看日志是"出了问题才去看"。原始的数字要人去判断"0.68 算高还是低",
而加一句告警,日志就从"数据"变成了"结论"。

阈值可配 `rag.logs.low-score-threshold=0.75`。**但这一点我想听你的意见**:
当前嵌入模型的中文分数普遍挤在 0.6~0.69,"正常"和"异常"很难用一个阈值分开,
设 0.75 会导致几乎每次都告警(变成噪音)。**或者干脆先不设告警,只打分数?**

### 💡 意见 3:比日志更好用的,是一个"检索调试接口"

日志是**事后**翻的。但排查 RAG 时,你真正想做的是"**我换句话问问看,召回变了没有**"。

建议顺手把现有 `POST /api/kb/search` 的响应**加上 `score` 和 `rank` 字段**
(现在的响应只有 id/heading/source/text,**分数被丢掉了**)。

这样可以直接在 Knife4j 里改 query 反复试,不用去日志里翻。

**成本很低**(只改 `KnowledgeBaseController` 里组装响应的几行),但排查效率提升明显。
—— 你觉得要不要加?

### 💡 意见 4:最高级别应该能打出「最终发给模型的完整 prompt」

排查 RAG 时有个经典难题:**答案不对,到底是"没检索到"还是"检索到了但模型没用"?**

只打召回内容无法区分这两者。要区分,必须看**最终拼装后、真正发给模型的那个 prompt**
(含 system 提示词 + 参考资料 + 历史对话)。

所以我设计了 `prompt` 这一档。但它最占空间(一次可能上万字),
建议**默认不开,需要时改配置开**。

### 💡 意见 5:详细日志的代价,要有心理准备

按 `full` 档、每次请求 5 条正文估算,**一次对话大约产生 3~8KB 详细日志**。
频繁使用的话一天可能几十 MB。

对策已包含在方案里(独立文件 + 3 天保留 + 大小轮转),但你**需要知道这个量级**。
若觉得太占地方,可把默认档调成 `brief`,需要时再开 `full`。

### 💡 意见 6:关于"打印问答内容"的隐私边界

详细日志会把**用户提问原文**和**手册正文**写进磁盘。本地自用没问题。

但提醒一句:**如果你把日志导出、发给别人帮忙排查,手册正文和你的提问就一起出去了。**
所以 `localhost-only` 这个默认我建议保留。
