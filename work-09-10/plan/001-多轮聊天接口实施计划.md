## 1. 目标与范围

### 1.1 目标

把现有的**单轮聊天接口**升级为**支持上下文的对话接口**,使同一会话内模型能记住之前的问答。

### 1.2 范围内

- `POST /api/chat` 支持会话标识,连续调用能带上历史上下文
- 会话生命周期管理(新建、清空)
- 会话隔离(不同会话互不串味)
- 保留对现有单轮调用方的向后兼容

### 1.3 明确不在范围内(本期不做)

| 项 | 原因 |
|---|---|
| 把 RAG 检索接入对话链 | 是独立议题:`ChatService` 目前是裸调模型,`KnowledgeBaseService.search` 未挂进对话。见 `002` 计划 |
| 聊天记录持久化(MySQL/Redis) | 本期用进程内记忆,重启即失效;持久化在阶段 4 再评估 |
| 流式输出(SSE) | 与多轮记忆正交,可后续单独做 |
| 前端页面 | 本项目当前无前端 |
| 修复 Milvus 启动慢 / 导入重复 | 独立议题;本改动**不依赖 Milvus**,见 §7.1 |

## 2. 现状(已逐项核实)

### 2.1 现有接口

`ChatController` → `ChatService` → `ChatClient`:

```java
// ChatController.java:25-29
@PostMapping
public ChatResponse chat(@RequestBody ChatRequest request) {
    return chatService.chat(request.message());
}

// ChatService.java:23-29
public ChatResponse chat(String message) {
    String reply = chatClient.prompt().user(message).call().content();
    return new ChatResponse(reply);
}
```

- `ChatRequest` = `record(String message)`
- `ChatResponse` = `record(String reply)`
- **无任何记忆、无 conversationId、无 advisor**

### 2.2 关键有利条件(已验证,非推测)

我反编译了本地 `.m2` 中的 Spring AI 2.0.0 产物,确认以下事实,**这些直接决定本计划的实现路径**:

| 事实 | 证据 |
|---|---|
| `spring-ai-autoconfigure-model-chat-memory-2.0.0.jar` **已在运行时 classpath 上**(经 `spring-ai-starter-model-openai` 传递引入) | 项目 `run.args` 的 classpath 里存在该 jar |
| 该 jar 通过 SPI 自动注册了 `ChatMemoryAutoConfiguration` | jar 内 `AutoConfiguration.imports` 内容为 `org.springframework.ai.model.chat.memory.autoconfigure.ChatMemoryAutoConfiguration` |
| 它是 `@AutoConfiguration` + `@ConditionalOnClass({ChatMemory, ChatMemoryRepository})`,两个 `@Bean` 均为 `@ConditionalOnMissingBean` | `javap -v` 注解表 |
| 因此**开箱即有一个 `ChatMemory` bean**,无需自建 | 该配置的 `chatMemory(ChatMemoryRepository)` 方法体:`MessageWindowChatMemory.builder().chatMemoryRepository(repo).build()` |
| 默认 `ChatMemoryRepository` 是 `InMemoryChatMemoryRepository`,底层 `Map` | `javap -p` 字段 `Map<String, List<Message>> chatMemoryStore` |
| `MessageWindowChatMemory.Builder` 的 `maxMessages` 默认值为 **20** | `Builder` 构造器字节码 `bipush 20; putfield maxMessages` |
| 20 是**消息条数**而非对话轮数 → 约等于 **10 轮**问答 | 同上 |
| `ChatMemory.CONVERSATION_ID` 常量值为 **`"chat_memory_conversation_id"`** | `javap -constants` |
| `MessageChatMemoryAdvisor` 提供 `builder(ChatMemory)`,支持 `.order(int)` / `.scheduler(...)` | `javap` |

### 2.3 一个必须先知道的框架行为(坑)

`BaseChatMemoryAdvisor.getConversationId(Map)` 的字节码逐条还原为:

```java
default String getConversationId(Map<String, Object> context) {
    Assert.notNull(context, "context cannot be null");
    Assert.noNullElements(context.keySet().toArray(), "context cannot contain null keys");
    Assert.notNull(context.get(ChatMemory.CONVERSATION_ID), "conversationId cannot be null");
    return context.get(ChatMemory.CONVERSATION_ID).toString();
}
```

**结论:只要挂了 `MessageChatMemoryAdvisor`,每一次请求都必须显式传 `ChatMemory.CONVERSATION_ID` 参数,否则直接抛 `IllegalArgumentException: conversationId cannot be null`。**

它**不会**静默退化成一个默认会话(这点和很多人对 Spring AI 的印象相反,已实测字节码确认)。好处是失败即暴露、不会互相串味;代价是 `ChatService` 里没有任何"忘了传"的余地。

## 3. 方案选型

| | 方案 A:服务端记忆 + conversationId | 方案 B:无状态,客户端传全量历史 | 方案 C:持久化记忆 Repository |
|---|---|---|---|
| **做法** | 挂 `MessageChatMemoryAdvisor`,请求带 `conversationId`,服务端按会话存历史 | 请求带 `messages[]`,服务端每轮拼全量历史,不存任何状态 | 同 A,但 `ChatMemoryRepository` 换成 JDBC/Redis 实现 |
| **改动量** | 小(4 个文件) | 中(需重定义请求结构 + 客户端改造) | 中(A + 新依赖 + 建表) |
| **客户端负担** | 只记一个 ID | 需自行维护并回传完整历史 | 只记一个 ID |
| **Token 消耗** | 服务端可窗口截断,可控 | 客户端无节制回传,易爆 | 同 A |
| **重启后** | 记忆丢失 | 不丢 | 不丢 |
| **多实例部署** | 不共享(会串会话) | 天然支持 | 取决于存储 |
| **与后续 RAG 接入的兼容性** | 好(advisor 链天然可叠加) | 好(但两套拼装逻辑) | 好 |

### 推荐:**方案 A**

理由:

1. 改动最小且**完全复用框架官方机制**,不自己造消息拼装逻辑
2. `ChatMemory` bean 已经自动就绪(见 §2.2),几乎零配置成本
3. 请求只多一个可选字段,**现有单轮调用方不用改**(见 §4.2 的兼容策略)
4. advisor 链是 Spring AI 的既定扩展点,之后接 RAG 检索 advisor 时可以直接往上叠,不用重构

方案 B 的"客户端无节制回传历史"在本项目尤其危险——本地 `gemma-4-e2b` 跑在 **4 GB 显存**的 RTX 3050 Laptop 上,prompt 一长延迟和显存都会迅速恶化,窗口必须由服务端把关。

方案 C 上期不做,但 A 的实现会预留切换点(只换 `ChatMemoryRepository` bean,不动业务代码),见 §6 阶段 4。

## 4. 接口契约设计

### 4.1 新增/变更端点

#### `POST /api/chat` —— 多轮对话(变更)

请求体:

```json
{
  "conversationId": "可选。不传或为空 → 服务端生成一个新的并随响应返回",
  "message": "我叫张三,请记住"
}
```

响应体:

```json
{
  "conversationId": "3f2a9c1e-...",
  "reply": "好的,张三,我记住了。"
}
```

第二轮(带上上一轮返回的 ID):

```json
{ "conversationId": "3f2a9c1e-...", "message": "我叫什么?" }
```

→ `reply` 应包含"张三"。

#### `DELETE /api/chat/{conversationId}` —— 清空会话(新增)

调用 `ChatMemory.clear(conversationId)`,用于"开启新话题"。返回:

```json
{ "conversationId": "3f2a9c1e-...", "cleared": true }
```

#### `GET /api/chat/{conversationId}/messages` —— 查看会话记忆(新增,调试/联调用)

返回当前窗口内的 `Message` 列表(角色 + 内容),便于验证记忆确实生效、且窗口截断符合预期。

### 4.2 向后兼容策略(重要)

`conversationId` 设计为**可选**:

- **不传** → 服务端 `UUID.randomUUID()` 生成,当次会话仅存在于该请求内 → **行为等价于现在的单轮接口**,老调用方零改动
- **传** → 走多轮

这样 `/api/chat` 的契约是"加字段"而非"改语义",不存在破坏性变更。

## 5. 详细改动清单

> 以下为**计划中的目标形态**,不是已完成的改动。代码骨架用于说明实现意图,实际落地时按此施工。

### 5.1 `dto/ChatRequest.java`

`record` 增加 `conversationId` 字段(置于 `message` 之前或之后均可,建议放前面以体现"先定会话、再说话"):

```java
@Schema(description = "聊天请求(conversationId 为空则视为一次性单轮对话)")
public record ChatRequest(
        @Schema(description = "会话 ID。首轮不传,服务端生成并在响应中返回;后续轮次回传以延续上下文",
                example = "3f2a9c1e-8b7d-4a2f-9c11-0d5e6f7a8b9c")
        String conversationId,

        @Schema(description = "用户输入的消息内容", requiredMode = Schema.RequiredMode.REQUIRED)
        String message
) { }
```

⚠️ 注意:`record` 的规范构造器签名会变化。若反序列化用 Jackson(默认按组件名匹配),**JSON 字段名不变**,故兼容;但如果有测试直接 `new ChatRequest("你好")`,需同步改为双参。

### 5.2 `dto/ChatResponse.java`

```java
@Schema(description = "聊天响应")
public record ChatResponse(
        @Schema(description = "本次对话的会话 ID,后续轮次需回传")
        String conversationId,

        @Schema(description = "模型回复内容")
        String reply
) { }
```

同理,`new ChatResponse(reply)` 的调用点(`ChatService`)需同步改。

### 5.3 `config/ChatConfig.java` —— 挂上记忆 advisor

当前实现只注入裸 `ChatClient.Builder`。改为:

```java
@Configuration
public class ChatConfig {

    @Bean
    public ChatClient chatClient(ChatClient.Builder builder, ChatMemory chatMemory) {
        return builder
                .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
                .build();
    }
}
```

- `ChatMemory` 由框架自动配置提供,这里**只注入不新建**(见 §2.2),这样窗口大小用的是框架默认 20 条
- 如需把窗口大小做成可配置项(推荐,见 §5.6),则改为在本类中显式声明 `ChatMemory` bean,利用 `@ConditionalOnMissingBean` 覆盖默认

### 5.4 `service/ChatService.java` —— 会话 ID 处理

```java
public ChatResponse chat(String conversationId, String message) {
    String cid = (conversationId == null || conversationId.isBlank())
            ? UUID.randomUUID().toString()
            : conversationId;

    String reply = chatClient.prompt()
            .user(message)
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, cid))  // ← 必须传,否则抛异常
            .call()
            .content();

    return new ChatResponse(cid, reply);
}
```

再补两个方法供控制器调用:

```java
public void clear(String conversationId)              // → chatMemory.clear(conversationId)
public List<Message> history(String conversationId)   // → chatMemory.get(conversationId)
```

需要把 `ChatMemory` 也注入 `ChatService`(用于 `clear` / `get`),或单独建一个 `ConversationService` 承载体贴会话管理职责——**建议后者**,让 `ChatService` 只负责"对话",会话生命周期归 `ConversationService`,职责更清晰(见 §6 阶段 2)。

### 5.5 `controller/ChatController.java`

```java
@PostMapping
public ChatResponse chat(@RequestBody ChatRequest request) {
    return chatService.chat(request.conversationId(), request.message());
}

@DeleteMapping("/{conversationId}")
public Map<String, Object> clear(@PathVariable String conversationId) { ... }

@GetMapping("/{conversationId}/messages")
public Map<String, Object> history(@PathVariable String conversationId) { ... }
```

同步更新 `@Operation` / `@Tag` 的 `description`——现在它写的是"单轮对话相关接口",会与实际能力不符。

### 5.6 `application.properties` —— 把窗口大小外置(建议)

在 §5.3 的自定义 `ChatMemory` bean 中读取:

```properties
# ============ 多轮会话记忆 ============
# 记忆窗口保留的消息条数(1 轮问答 = 2 条消息),超出后丢弃最早的
rag.chat.memory.max-messages=20
```

好处:4 GB 显存场景下可以随时把窗口调小做对比,不用改代码重新构建。

## 7. 风险、坑与对策

### 7.1 好消息:本改动**完全不依赖 Milvus**

多轮记忆只需要 `ChatClient` + `ChatMemory`,不需要向量库。而 Milvus 恰恰是当前环境里最不稳定的部分(WSL 已 Stopped,`pipeline.log` 记录了多次 `engine bounced`、140s 不健康的重试)。

**因此本计划可以在不启动 Docker/WSL 的前提下独立开发和验证**,LM Studio 当前已在 1234 端口运行且模型与 `application.properties` 一致。这是本计划风险最低的部分,不要把它和 Milvus 的坑搅在一起。

### 7.2 风险清单

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 忘了传 `ChatMemory.CONVERSATION_ID` | **每次请求直接抛异常**(§2.3 已实测) | 只在 `ChatService` 一处拼装 prompt,统一传参;加一个 `@SpringBootTest` 冒烟用例覆盖 |
| 2 | 所有会话串味 | 严重(隐私/串话) | 会话 ID 用服务端生成的 UUID;不接受客户端传空串当有效 ID;阶段 1 用两个 ID 交叉验证 |
| 3 | `maxMessages=20` 的理解偏差 | 以为 20 轮、实际 10 轮 | 明确文档化;§5.6 外置以便实测 |
| 4 | 会话永不释放 → 内存泄漏 | 长跑 OOM | 阶段 3 加 TTL 淘汰;当前 `InMemoryChatMemoryRepository` **无任何淘汰机制** |
| 5 | 长历史拖慢推理 | 4 GB 显存下延迟上升/显存不足 | 窗口大小设保守值;必要时配合 `LastMaxTokenSizeContentPurger` |
| 6 | 窗口截断丢掉 system prompt | 人设/约束失效 | 当前无 system prompt,暂无影响;将来加 system 时需确认 `MessageWindowChatMemory` 的保留策略 |
| 7 | 多实例部署串会话 | 会话随机漂移 | 单机开发无影响;上线多实例前必须走阶段 4 持久化 |
| 8 | **无 Maven,构建方式受限** | 改完无法命令行构建 | 见 §8.1 |
| 9 | 记忆 + 未来 RAG 两个 advisor 的顺序 | 检索结果可能不进记忆或反之 | 接 RAG 时显式设定 `.order(...)`,不要依赖默认值 |
| 10 | `ChatRequest`/`ChatResponse` 构造器签名变化 | 编译报错 | 一次性改完调用点(`ChatService`、测试) |

## 8. 构建与验证

### 8.1 构建方式(环境约束)

`mvn` **未安装**,项目也**没有 `mvnw`** → 命令行无法用 Maven 构建。

| 方式 | 说明 |
|---|---|
| **IDEA 构建/运行(推荐)** | 项目已配置 Maven 集成(`.idea/misc.xml` 指向 `rag/pom.xml`),Project SDK = `openjdk-23`。用 IDEA 编译运行,与既有产物保持一致 |
| 手动 `javac`(备用) | 依赖已全在 `~/.m2`,且 `target/cp.txt` 存有完整 classpath。可用 `~/.jdks/openjdk-23.0.2/bin/java` + `-cp "target\classes;$(cat target\cp.txt)"` 直接跑(此前那批导入脚本正是这么做的) |

⚠️ PATH 上的 `java` 是 **JDK 11**,低于 pom 要求的 21,**不能**直接用它跑。必须用 IDEA 或显式指定 `~/.jdks/openjdk-23.0.2`。

⚠️ `pom.xml` 声明 `java.version=21`,而脚本运行用 JDK 23。建议统一经 IDEA 构建,避免 class 文件版本与 target 不一致。

### 8.2 验证步骤

**前置**:确认 LM Studio 已加载模型(当前已满足):

```powershell
(Invoke-WebRequest 'http://127.0.0.1:1234/v1/models' -UseBasicParsing).Content
# 期望包含: google/gemma-4-e2b 与 text-embedding-nomic-embed-text-v1.5
```

**用例 1 — 单轮兼容(不传 conversationId)**

```powershell
curl.exe -s -X POST http://127.0.0.1:8080/api/chat -H 'Content-Type: application/json' `
  --data-binary '{"message":"你好"}' --max-time 120
# 期望: 200,响应含新生成的 conversationId(reply 正常)
```

**用例 2 — 多轮记忆(核心验收)**

```powershell
# 第 1 轮:记名字,取出 conversationId
$r1 = curl.exe -s -X POST http://127.0.0.1:8080/api/chat -H 'Content-Type: application/json' `
  --data-binary '{"message":"我叫张三,请记住我的名字"}' --max-time 120 | ConvertFrom-Json
$cid = $r1.conversationId

# 第 2 轮:带上同一个 ID 追问
curl.exe -s -X POST http://127.0.0.1:8080/api/chat -H 'Content-Type: application/json' `
  --data-binary ('{"conversationId":"' + $cid + '","message":"我叫什么名字?"}') --max-time 120
# 期望: reply 中包含「张三」
```

**用例 3 — 会话隔离**

用另一个 `conversationId` 问"我叫什么名字?",期望模型**答不出**(不应出现"张三")。

**用例 4 — 会话清空**

```powershell
curl.exe -s -X DELETE "http://127.0.0.1:8080/api/chat/$cid" --max-time 30
# 再用同一 $cid 问"我叫什么名字?",期望: 已遗忘(回到无上下文状态)
```

**用例 5 — 记忆可观测**

```powershell
curl.exe -s "http://127.0.0.1:8080/api/chat/$cid/messages" --max-time 30
# 期望: 返回角色交替的消息列表;超过窗口后老消息被丢弃
```

**用例 6 — 文档可用**

访问 `http://127.0.0.1:8080/doc.html`(Knife4j),确认三个聊天端点均出现在"聊天接口"分组且描述已更新。

### 8.3 验收标准

- [ ] 用例 1 通过:老的单轮调用方式行为不变
- [ ] 用例 2 通过:同 ID 连续两轮,模型记住第一轮信息
- [ ] 用例 3 通过:不同 ID 之间无信息泄漏
- [ ] 用例 4 通过:清空后记忆确实失效
- [ ] 用例 5 通过:能观测到窗口内消息,且超过 `maxMessages` 后按预期丢弃
- [ ] 不传 `conversationId` 时**不抛异常**(§7.2 风险 1 已闭合)
- [ ] Knife4j 文档三个端点可用、描述准确

| 3 | 是否本期就做持久化 | **不做**。先用进程内记忆把多轮跑通 | 直接上 MySQL/Redis(需先定存储、加依赖、建表) |
| 4 | 是否顺带把 RAG 检索接进对话 | **不做**,独立成 `002` 计划 | 合并做(改动面显著变大,且引入 Milvus 依赖风险) |
